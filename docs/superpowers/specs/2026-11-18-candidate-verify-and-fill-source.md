## 1) AI 제한 해제 + AI가 만든 부분 색 표시

- `_compile_prompt`에서 "원문에 없는 날짜·이름을 지어내지 말고 원문에 나온 것 안에서만 고른다" 제한을 풀어서, AI가 맥락상 가장 그럴듯한 값으로 담당자·기한·범위를 채우게 한다
- 고정 예시 문장 "~은 다음 회의 전까지 단톡방에서 정한다"는 삭제한다. 필요하면 "누가 정하는지 + 언제까지"처럼 들어갈 요소만 설명한다
- AI에게 [회의 정보] 블록을 같이 준다: 회의 날짜(요일 포함, `Meeting.created_at`), 참석자 이름(`Meeting.participants` / 기존 `_participant_names`), `deadline`, 이전 회의의 미결정 안건(기존 `carryover_decisions`). 전사본의 "화자 A/B"가 참석자 중 한 명이라는 설명도 넣는다
- 애매 항목 JSON에 `fills` 배열을 추가한다: `[{"gap": "기한|담당|범위|선택지", "value": "채운 값", "source": "원문|회의정보|AI추정", "quote": "원문 인용(원문일 때만)"}]`
- 서버가 검증한다: source가 "원문"인데 quote가 전사본에 없으면 "AI추정"으로 바꾼다. "회의정보"는 실제 회의 정보에 그 값이 있는지 확인하고, 없으면 "AI추정"으로 바꾼다
- 진행자 화면(결정 카드)에서 추천 문장 안의 AI추정 값을 다른 색으로 강조하고, "AI가 추정한 값이 있어요: 기한"처럼 경고 한 줄을 띄운다. 원문·회의정보 값은 표시하지 않는다
- 바로 공개되는 명확(`ambiguous: false`) 항목의 `final`은 지금처럼 원문 기준을 유지한다. 제한 해제는 진행자가 고르는 애매 항목의 추천 문장에만 적용한다

## 2) 추천 문장 검증 → 1회 재생성 → 그래도 걸리면 폐기

- 새 파일 `APL_04/meetalign/decision_checks.py`에 순수 함수로 작성 (Django·LLM 의존 없이)
  - 원문 유사도 검사: candidate와 evidence의 글자 bigram 겹침이 임계값 이상이면 걸림 (기존 `_bigrams` 재사용 가능)
  - 새 정보 검사: candidate에는 있는데 evidence에는 없는 날짜·시각·숫자·참석자 이름 토큰이 0개면 걸림 (기존 `_date_tokens`·`_time_tokens`·`_quantity_tokens` 재사용)
  - 결정끼리 중복 검사: 같은 회의 안에서 다른 결정의 candidate나 final과 거의 같으면 걸림
  - 입력: candidate, evidence, 다른 결정 문장 목록, 참석자 이름 / 출력: (통과 여부, 걸린 이유 목록)
- 재생성: 걸린 결정만 모아서 AI를 한 번 더 부른다. 걸린 이유, 그 결정 근거의 앞뒤 대화(기존 `context_around`), 회의 정보, 다른 결정 문장들을 같이 주고 "이 문장들과 겹치지 않게, 이유를 고쳐서" 다시 쓰게 한다. 걸린 게 없으면 호출하지 않는다
- 재생성은 1회만. 다시 검사해서 그래도 걸리면 추천 문장을 폐기하고 기존 `draft_hint` / 직접 쓰기 흐름으로 보낸다
- 이 전체를 `refine_candidates(items, source, meeting_info) -> items` 함수 하나로 묶는다. 호출 흐름(추출·판정·생성 단계 분리)은 건우 님이 따로 작업하므로 `compile_specs`는 최소한만 고친다: 생성이 끝난 뒤 저장 전에 `refine_candidates`를 한 줄로 부르는 것까지만. origin에 건우 님의 단계 분리 브랜치가 있으면 먼저 알려주고, 겹치는 부분을 어떻게 맞출지 물어본다

## 3) 기록

- 검증 결과(걸린 이유, 재생성 성공 여부, 폐기 여부)를 `compile_meeting` 결과 dict와 서버 로그에 남긴다. 나중에 재생성 성공률을 보고 이 단계를 유지할지 정하려는 용도다

## 지키기

- 진행자·팀원이 입력하거나 설정할 것을 늘리지 않는다
- `MAX_INTERPRETATIONS = 1`, 진행자가 고르는 흐름은 유지한다
- 테스트에서 실제 LLM/API를 호출하지 않는다 (기존 테스트처럼 mock)
- 기존 테스트는 전부 통과해야 한다. 기존 테스트를 바꿔야 하면 이유를 먼저 설명하고 확인을 받는다
- 마이그레이션이 필요하면(fills 저장 등) 먼저 알린다
- 끝나면 `python manage.py test` 결과, 바뀐 프롬프트 전문, 화면 변경 설명, PR 설명 초안을 보여준다. push와 PR 생성은 팀에서 한다
